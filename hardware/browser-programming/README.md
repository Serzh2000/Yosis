# Первое браузерное подключение Tang Nano 20K

Проверка 2 октября 2026: WebUSB видит USB-устройство. После выбора браузер открывает устройство, но `claimInterface(0)` завершается `Unable to claim interface`. До MPSSE и инструкций FPGA выполнение не доходит; SRAM и flash этой попыткой не изменены.

Независимое чтение Windows PnP показывает `FTDIBUS` для interface A (`MI_00`) и B (`MI_01`). D2XX перечисляет location 529/530, serial `2025030317A/B`, flags `2`: интерфейсы присутствуют и не открыты другой программой. Это соответствует ограничению WebUSB на Windows, где доступ приложений к интерфейсу требует WinUSB. Драйверы и BL616 не изменялись.

Браузер через выбор локального файла успешно прочитал `../clocked-pattern/design.fs`, проверил CRC всех кадров и показал SHA-256 `7549f57d31ee6a1bd48bf3bfc4da8a80a2e63b60dc48cdbeecfaf1e2cceb3115`. Кнопка записи остаётся заблокированной, поскольку JTAG-доступ не подтверждён. Необработанных ошибок в консоли проверочной вкладки нет.

Результат: браузерный код и офлайн-проверки есть; штатная Windows-конфигурация платы пока не поддерживает прямую запись. Для школьного сценария без установки программ требуется совместимый USB-интерфейс отладчика. Проверять это нужно отдельно; прежний успех Gowin Programmer не подтверждает WebUSB.

[Сценарий и ограничения](../../docs/browser-programming.md) · [Требования Chrome к WinUSB](https://developer.chrome.com/docs/capabilities/build-for-webusb).

## Штатный ROM BL616

Пользователь подключил плату с зажатой UPDATE. Read-only Windows PnP подтвердил штатный ROM USB `349b:6160`, класс Ports, COM12 и встроенный сервис `usbser`; установки и изменения драйвера не было. Локальный снимок: `.physical/browser-rom-devices.json`.

Первый фильтр из Python-инструмента Bouffalo учитывал только `ffff:ffff` и `42bf:b210`, поэтому список браузера оказался пустым. Добавлен реально обнаруженный ID и тест. Показанное имя Windows — «Устройство с последовательным интерфейсом USB (COM12)».

Read-only Web Serial probe успешно прочитал настоящий ROM: версия `0x06160001`, подпись IF `0`, шифрование IF `1`. Сырой ответ: `01001606000101002792800135b7f50286241a000f758010`. Локальная запись: `.physical/browser-rom-bootinfo.json`.

Переданы только handshake и `10 00 00 00`, затем порт закрыт. Консоль браузера без ошибок. Образ не загружался, SRAM FPGA, flash и eFuse не менялись. Шифрование IF не доказывает запрет отдельного нативного пути flash ROM. [Исследование openFPGALoader_webUSB и ROM](../../docs/browser-programming-research.md).

## Установщик DirtyJTAG — 3 октября

Подготовлен настоящий комплект из закреплённых DirtyJTAG/SDK и загрузчика Sipeed. Добавлены MS OS 2.0/WinUSB для JTAG, отдельный CDC UART, установка и восстановление с полной копией IndexedDB. Общие тесты прошли 298/298; аппаратная запись пока не подтверждена. [Образы, хэши и протокол](../dirtyjtag/README.md).

После инструкции UPDATE пользователь сообщил о продолжающемся бегущем огне. Read-only PnP подтвердил именно ROM: `USB\\VID_349B&PID_6160`, «Устройство с последовательным интерфейсом USB (COM12)». Работа LED не является признаком режима USB-отладчика: FPGA запускает свою программу независимо.

## Граница подтверждения после ревью

Ранее прочитан JEDEC `c8601600` (4 МиБ, pin 2). Подготовка останавливалась на параметрах flash, таймауте и `FL 0x0102` (ошибка длины команды по host-инструменту). Полная резервная копия, запись и последующая USB-идентичность DirtyJTAG достоверно не подтверждены. Сообщение UI без независимого подтверждения устройства не считается успешным аппаратным испытанием.

Во время полного ревью запись не выполнялась. Исправлены бюджет SHA и запись boot header последним; обнаружены отдельные проблемы C firmware, ещё не исправленные в бинарнике. Проверка PnP в конце ревью показала только Bluetooth COM-порты; устройство Tang в этом снимке не присутствовало. [Полный разбор](../../docs/dirtyjtag-install-review.md).
