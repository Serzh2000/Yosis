# Ревью установки DirtyJTAG на Sipeed Tang Nano 20K

> Обновление 4 октября 2026: опубликован **dirtyjtag-v2-yosis-winusb-3**. Замечания к C-границам/владению USB и применению настроек UART исправлены в overrides и пересобранном образе. Native harness исполняет настоящий C-обработчик: 14 групп и 20 000 пакетов с UBSan. Добавлены повторный выбор ROM-порта, reset при disconnect и защищённые серверные копии с проверкой до записи. Старые разделы находок ниже описывают причину изменений. Полная аппаратная приёмка новой версии остаётся открытой.

Дата: 3 октября 2026. Проверены процедура, исходники, двоичные образы, браузерный установщик и восстановление.

## Вывод

**Путь через UPDATE → Web Serial → прошивку BL616 технически обоснован. Готовность для школьного использования пока не подтверждена.** Адреса нашего комплекта согласованы с закреплённым коммитом DirtyJTAG. Полный аппаратный цикл ещё не пройден; в исходниках самого отладчика найдены ошибки, которые нужно устранить до массовой установки.

В ходе ревью исправлены таймаут проверки flash, порядок записи загрузчика, проверка профиля ROM и подсказки подключения. Двоичный образ DirtyJTAG в этом ревью не заменялся, запись на плату не запускалась.

## 1. Что именно перепрошивается

На плате есть несколько независимых компонентов:

| Компонент | Назначение | Действие установщика |
| --- | --- | --- |
| FPGA GW2AR-LV18QN88C8/I7 | Пользовательская логика | Через DirtyJTAG отдельной операцией загружается SRAM |
| SDRAM 64 Мбит / 8 МиБ | Память для логики FPGA, например RISC-V | Установщик BL616 её не использует |
| Flash FPGA | Битстрим после включения питания | Установщик BL616 к ней не обращается |
| BL616 и его flash | USB-отладчик и UART | Здесь заменяется FTDI-эмуляция |

Наличие SDRAM не меняет процедуру установки отладчика. [Описание платы Sipeed](https://wiki.sipeed.com/hardware/en/tang/tang-nano-20k/nano-20k.html).

Это обновление прошивки микроконтроллера. Новый USB-интерфейс объявляет совместимость с системным WinUSB; установка драйвера FTDI на компьютере не редактируется приложением.

## 2. Два разных способа загрузки вторичной прошивки

| Вариант | Образ по адресу 0 | Вторичная прошивка | Особенность |
| --- | --- | --- | --- |
| Старый partner/TangCore | Штатная partner firmware Sipeed | `0x40000` | README DirtyJTAG описывает зависимость перехода от обнаружения USB |
| Наш закреплённый комплект | `bl616_bootloader_0x20000_nano20k_signed.bin` | `0x20000` | Автор коммита сообщает о безусловном переходе во вторичную прошивку |

Для Yosis используется второй вариант. `flash_prog_cfg.ini` и манифест совпадают. Старые инструкции про `0x40000` и питание без USB-data к этому комплекту применять нельзя. Это следует из [коммита `64fe564b`](https://github.com/pepijndevos/bl616_dirtyjtag/commit/64fe564b82e509e9aa0ff3372a95ca5e2edf9230), который изменил образ загрузчика и адрес одновременно.

Слово `signed` в имени файла не является нашей проверкой цифровой подписи. Декодированный boot configuration содержит `sign=0`, `encrypt=1` (AES-128). SHA-256 подтверждает соответствие выбранному upstream-файлу. Происхождение от Sipeed и переход на `0x20000` заявлены автором коммита; отдельного опубликованного Sipeed хэша для этого конкретного загрузчика в проверенных источниках нет. Загрузчик закрытый, его выполнение ещё нужно подтвердить на плате.

## 4. Последовательность установки

1. Отключить USB. Удерживая UPDATE за HDMI, подключить USB, отпустить кнопку. Это штатный вход в ROM BL616. [Инструкция Sipeed](https://wiki.sipeed.com/hardware/en/tang/common-doc/update_debugger.html).
2. В мастере выбрать последовательный порт Bouffalo CDC. На нашей Windows-плате наблюдался `349b:6160`, COM12, системный `usbser`. Номер COM может отличаться. Верхняя кнопка выбора USB/JTAG относится к следующему этапу.
3. Прочитать BootInfo, JEDEC и всю flash BL616. Проверить SHA на устройстве и в браузере, сохранить и перечитать IndexedDB-копию. До завершения подготовки команд стирания и записи содержимого нет.
4. Показать пользователю идентификатор платы, ёмкость flash, хэш копии и количество изменяемых секторов.
5. Повторно открыть ROM, проверить ту же плату и неизменность flash. Записать изменившиеся секторы: вторичная прошивка, тело загрузчика, сектор 0 с boot header. Проверить каждый сектор и всю flash.
6. Переподключить USB без UPDATE. Ожидается `1209:c0ca`; для JTAG нужен WinUSB на interface 0, для UART — отдельный CDC-порт.
7. Выбрать устройство в WebUSB, получить `DJTAG2`, прочитать ожидаемый FPGA IDCODE и загрузить контрольный битстрим в SRAM. Только после этих проверок считать путь рабочим.

Работающий бегущий огонь при удержании UPDATE не опровергает вход в ROM: FPGA может исполнять ранее сохранённый битстрим. Режим отладчика определяется USB и ответом BootInfo.

## 5. Протокол ROM и flash

Проверяемые файлы: `src/lib/bl616-flash.ts`, `debugger-install.ts`, `debugger-backups.ts`.

Используется нативный путь flash (`load_function=2` в host-инструменте). Загрузка собственного RAM/IF-loader не требуется в выбранной реализации. BootInfo с `encrypt=1` сам по себе не доказывает запрет отдельных команд flash.

| Команда | Назначение | Проверка реализации |
| --- | --- | --- |
| `0x10` | BootInfo | Поля BL616, версия и профиль защиты |
| `0x22` | Тактирование / скорость | Два uint32 LE; CDC открывается на 115200 |
| `0x3B` | Настройка flash | Pin из BootInfo, далее закреплённые параметры при необходимости |
| `0x36` | JEDEC | ID, флаг таблицы, ёмкость и пределы |
| `0x32` | Чтение | Адрес/длина LE, точная длина ответа |
| `0x30` | Стирание сектора | 4096 байт; конечный адрес включительно |
| `0x31` | Запись | Адрес и данные, проверка ACK |
| `0x3A` | Проверка записи | Выполняется после данных сектора |
| `0x3D` | SHA-256 raw flash | Сравнение с SHA браузера |

Формат кадра, checksum и LE-поля совпадают с проверенным host-исходником. ACK `OK`, ошибка `FL` и ожидание `PD` обрабатываются отдельно. Команды памяти, eFuse, chip erase и исполнения образа отсутствуют. При ошибке сессия закрывается, автоматического повторения записи нет.

### Наш JEDEC `c8601600`

Первые три байта — `c8 60 16`, ёмкость 4 МиБ. Последний байт `00` не подтверждает встроенную таблицу параметров ROM. Поэтому первичная попытка правильно остановилась до стирания.

Добавлен 84-байтный `flash_para.bin` из закреплённого SDK, SHA-256 `002c41f38bb652bdaf89136183aaef70ae11abbf85f554a59d7242748f32e1e0`. Этот SDK-файл содержит параметры GigaDevice; его соответствие `c86016` дополнительно согласуется с [реализацией автора M0SSFlash](https://github.com/philmillman/M0SSFlash). Он не является дампом таблицы нашей mask ROM. После передачи параметров повторно проверяется JEDEC. Другие неизвестные ID с флагом `00` отклоняются.

Полное чтение 4 МиБ и команды записи на настоящей ROM ещё не подтверждены. Размер 2048 байт согласован с host-буфером 2056 байт; это не доказывает устойчивость таких кадров в конкретной USB CDC ROM. M0SSFlash использует существенно меньшие блоки и паузы. Нужна аппаратная проверка чтения и ACK; утверждать универсальный предел ROM в 64 байта по одному чужому комментарию нельзя.

## 6. Замечания ревью

### P1: аппаратная цепочка остаётся непроверенной

Есть физические BootInfo и JEDEC. Нет достоверного завершённого чтения и резервирования всей flash, установки, новой USB-идентичности, назначения WinUSB, FPGA IDCODE через этот отладчик и восстановления. Модель ROM в тестах проверяет наш код, но сама не является mask ROM BL616.

Последние ошибки относятся к подготовке: параметры flash, таймаут, `FL 0x0102`. По [таблице host-инструмента](https://github.com/openbouffalo/bflb-mcu-tool/blob/9caeb5d7e01ce344227bbb34d20cb3a91f5c1545/bflb_mcu_tool/libs/bflb_utils.py) `0102` означает ошибку длины команды. Без стадии и чистого обмена нельзя определить, была ли это текущая команда или хвост handshake. Нельзя считать это ни отказом WinUSB, ни доказательством успешной записи. Ошибки теперь содержат стадию и opcode; добавлена очистка входа до handshake.

### P1: переполнение и неполные команды в firmware DirtyJTAG

`hardware/dirtyjtag/upstream/src/dirtyjtag.c`, функция `cmd_handle`:

- `CMD_FREQ`, `SETSIG`, `CLK` читают аргументы без проверки оставшейся длины пакета.
- `XFER` ограничивает число битов, но не проверяет наличие данных в полученном пакете.
- Суммарный ответ не ограничивается размером `tx_buf[64]`. Пакет `01 01 01 00` содержит три INFO и формирует больше 64 байт ответа: каждый INFO добавляет 10 байт и структуру UART debug.
- OUT повторно принимается до завершения IN; `ep_tx_busy` устанавливается, но не защищает `tx_buf` от перезаписи.

Обычный клиент Yosis передаёт ограниченные команды и ожидает ответы, что уменьшает вероятность сбоя. Прошивка всё равно должна сама проверять вход и владение буфером. Замечание подтверждено исходником; опасные пакеты на плату не отправлялись. Нужны проверка всего пакета до изменения GPIO, предел общего ответа, правильное ожидание IN и тесты C-обработчика. **Исправлено в опубликованном v3; аппаратная проверка отдельно.**

### P2: настройки UART объявлены, но игнорируются

В `upstream/src/uart_bridge.c` callback `usbd_cdc_acm_set_line_coding` ничего не делает. Функция применения настроек и флаг отложенной обработки есть, но callback их не активирует. UART остаётся на начальных 115200 независимо от выбранной скорости браузера. Кроме того, опрос UART отправляет данные без проверки `cdc_configured`, а TX callback передаёт байты через блокирующий `putchar` из USB callback.

Нужно реализовать отложенное применение скорости, корректную работу при закрытом CDC и проверить обмен после установки. Пока обещание произвольной скорости UART необоснованно.

### P2: замена partner firmware меняет дополнительные функции платы

Штатный BL616 управляет также MS5351 и предоставляет USB→SPI. В проверенном DirtyJTAG есть JTAG и UART; эквивалентов управления генератором и SPI-моста нет. Это видно из исходников и [перечня функций платы](https://wiki.sipeed.com/hardware/en/tang/tang-nano-20k/nano-20k.html). Работа основного 27 МГц источника и дополнительные тактовые выходы должны проверяться отдельно после полного выключения питания. Нельзя обещать сохранение всех функций штатного отладчика.

### P2: единственная резервная копия зависит от браузерного профиля

Сохранение до стирания, строгая транзакция и перечитывание реализованы. Однако IndexedDB может быть очищена пользователем или удалена браузером; `navigator.storage.persist()` не запрашивается, независимой копии нет. Восстановление означает возврат к самой ранней копии, сохранённой этим сайтом, а не доказанно к заводскому образу. На уже изменённой плате эти вещи различаются.

Для школьного сценария нужна политика сохранения копий без установки программ учениками: запрос persistent storage и/или защищённое серверное хранение с понятной привязкой к плате. Серверное хранение реализовано 4 октября. Установщик предупреждает об очистке профиля.

### P2: восстановление после сбоя требует явного выбора ROM-порта

Мастер переиспользует ранее разрешённый порт, в том числе после неудачи. Сам факт разрешения не гарантирует, что устройство всё ещё подключено или находится в BOOT. Теперь есть отдельный выбор нового ROM-порта после ошибки и сброс при disconnect. Нужно добавить этот переход и сбрасывать сохранённый порт при disconnect. Иначе пользователь может повторять подготовку на устаревшем объекте порта.

## 7. Исправлено в этом ревью

| Проблема | Исправление | Проверка |
| --- | --- | --- |
| SHA всей flash использовал обычные 3 с | Бюджет увеличивается с объёмом: 6 с для 4 МиБ, 18 с для 16 МиБ | Модель отвечает позже обычного таймаута; повторной команды нет |
| Заголовок загрузчика записывался раньше его тела | Сектор 0 записывается последним и при восстановлении | Проверен порядок полного многосекторного плана |
| Допускались неподтверждённые ROM/защита | Для текущего пакета оставлен наблюдённый `06160001`, sign 0, encrypt 1 | Другие профили отклоняются до настройки flash и стирания |
| FTDI-подсказка показывалась для DirtyJTAG | Подсказка зависит от выбранного адаптера | TypeScript, сборка, просмотр интерфейса |
| Обработчики JTAG/ROM не проверяли занятость установщика | Добавлен `setupBusy` в обработчики | TypeScript и общая регрессия |

Порядок «сектор 0 последним» уменьшает окно незавершённой загрузки; атомарной запись от этого не становится. Во время промежуточного состояния тело старого загрузчика уже может быть частично изменено. Для восстановления после потери питания нужен ROM BOOT и сохранённая копия.

## 8. WinUSB и сервер Linux

Сверены BOS 33 байта, MS OS 2.0 set 178 байт, индекс конфигурации 0 (в сборке winusb-1 ошибочно стояло 1; исправлено в winusb-2, bcdDevice 0x0202), function interface 0, `WINUSB`, GUID в UTF-16/REG_MULTI_SZ и vendor request `0x20`, index `7`. CherryUSB в выбранной конфигурации обрабатывает этот запрос. CDC-интерфейсы 1/2 не помечаются WinUSB. Full Speed согласован с bulk-пакетами 64 байта; callbacks qualifier/other-speed отключены.

Это соответствует механизму [Microsoft OS 2.0](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/microsoft-os-2-0-descriptors-specification) и назначению [системного WinUSB](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/automatic-installation-of-winusb). Реальная USB enumeration на Windows ещё не подтверждена. Наличие нужных байтов в файле не заменяет получение дескрипторов от работающего устройства.

Установщик — Web Serial; последующая работа JTAG — WebUSB. Браузер получает бинарники как обычные ресурсы сайта. Программы ученику устанавливать не требуется. Linux-сервер раздаёт эти ресурсы и результаты сборки; USB остаётся у клиента. Для публичного сайта необходим HTTPS. Собственный TS-транспорт DirtyJTAG не зависит от pthread/SharedArrayBuffer.

[openFPGALoader_webUSB](https://github.com/trabucayre/openFPGALoader_webUSB) — полезный источник для браузерного JTAG, но он не выполняет установку DirtyJTAG на BL616 и не устраняет Windows FTDI binding сам по себе. Повторная сборка нашего MCU-комплекта пока автоматизирована для Windows-разработчика; воспроизводимая Linux-сборка этого комплекта остаётся отдельной задачей.

## 9. Условия принятия реализации

1. Исправить C-обработчик DirtyJTAG и UART, пересобрать, обновить хэши, проверить новые бинарники.
2. На нашей плате в BOOT получить чистый обмен и прочитать всю flash дважды; сравнить хэши и SHA устройства. Это делается до любой записи.
3. Подтвердить сохранение копии и восстановление её из профиля после перезапуска браузера.
4. Установить проверенный комплект, проверить итоговую flash, переподключить USB.
5. На штатной Windows проверить WinUSB interface 0 и CDC UART без ручной установки драйверов.
6. Получить `DJTAG2`, верный FPGA IDCODE, выполнить контрольную SRAM-загрузку с заметным рисунком LED и проверить UART.
7. Вернуть BOOT, восстановить исходную копию, сравнить всю flash и убедиться, что возвращается штатный FTDI.
8. Повторить для других ревизий платы и выбранных клиентских ОС; только затем заявлять поддержку «любой штатной платы».

Программные проверки: 14 тестов ROM/flash в `tests/bl616-flash.test.ts`, вместе с read-only ROM — 24. Общий набор — 301 тест. Итоговые журналы и аппаратная граница проверки: [verification.md](verification.md), [hardware/browser-programming](../hardware/browser-programming/README.md).
