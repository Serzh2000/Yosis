# Полный план Yosis по переписке

Обновлено 4 октября 2026. Это общий план всех требований из чата, включая ревью Claude и последние замечания к интерфейсу.

## Цель и договорённости

Yosis — учебная мастерская для школьников: собрать устройство из элементов или описать его на Verilog, увидеть настоящую RTL-схему, проверить временные диаграммы и виртуальную плату, назначить выводы и запустить устройство на FPGA.

Целевая плата — Sipeed Tang Nano 20K, GW2AR-LV18QN88C8/I7, GW2A-18C, 64 Мбит встроенной SDRAM. Приложение работает на Linux-сервере. USB-плата подключена к компьютеру ученика: доступ к ней получает браузер. Ученикам не нужны локальные инструменты сборки, помощник или ручная установка драйверов.

Обозначения: **готово** — реализовано и проверено программно; **частично** — работает перечисленная часть, остальное явно указано; **нужна плата** — программные проверки есть, аппаратную приёмку ещё надо пройти. Интерфейс успешной операции сам по себе не доказывает работу всех аппаратных функций.

## 3. Код, RTL и технологическая схема — готово

- [x] Monaco с Verilog/SystemVerilog/CST, сниппетами и проверкой синтаксиса после паузы.
- [x] Настоящий Yosys: hierarchy → proc → opt для RTL, synth_gowin для Gowin.
- [x] Дерево модулей, ресурсы, раскрытие подмодулей; ограничение размера отображаемой схемы для больших проектов.
- [x] Обозначения вентилей, NOT, MUX, арифметики, сравнения, регистров с фронтом/сбросом/разрешением.
- [x] Проверки семантики обычных MUX и one-hot $pmux; контакты схемных символов и соединений используют одинаковую геометрию.
- [x] LUT INIT и таблица истинности; справочные карточки примитивов, параметров, LUT/FF/ALU/BRAM/DSP/I/O.
- [x] Переход из ячейки к сохранённой Yosys ссылке на HDL и подсветка по строке исходника.
- [ ] Двусторонняя навигация для автоматически созданного HDL: строка Verilog ↔ конкретный элемент .ysch.

RTL должен сохранять функциональную семантику исходников и использовать понятные схемные обозначения. Буквально одинаковый набор ячеек с Quartus не обещается: оптимизации и внутренние представления разных инструментов отличаются.

## 4. Графическое описание устройства — первая версия готова

- [x] Версионированный файл .ysch как исходник; отдельная вкладка «Конструктор».
- [x] 18 типов элементов: вход, выход, константа, NOT/AND/OR/XOR/NAND/NOR/XNOR, MUX, сумматор, вычитатель, сравнение, срез, объединение, дополнение нулями, регистр.
- [x] Шины 1–64 бит, явные ширины, пределы 200 элементов/2000 связей, стабильные ID.
- [x] Соединение контактов кликом или из списка, разветвление сигнала, перемещение элементов, undo/redo, масштаб и панорамирование.
- [x] Регистр: положительный внешний такт, синхронный сброс при 1, приоритет сброса над разрешением; без сброса начальное значение X.
- [x] Проверки несоединённых входов, нескольких источников, ширин, имён, значений, диапазонов и комбинационных петель. Обратная связь через регистр допустима.
- [x] Сохранение незавершённой схемы; строгая проверка перед сборкой, без замены недостающих сигналов нулями.
- [x] Прозрачный просмотр создаваемого Verilog; генерация на сервере перед запуском инструментов. Исходный .ysch не заменяется результатом Yosys.
- [x] Графический проект проходит тот же путь Yosys → Icarus → nextpnr → Apicula, что и HDL-проект.
- [x] Из внешнего порта конструктора можно перейти к назначению вывода платы.
- [ ] Выделение группы, копирование элементов, ручные точки проводов, удобное автоположение.
- [ ] Иерархические пользовательские блоки и схемные шаблоны счётчиков/автоматов.
- [ ] BRAM, PLL, DSP, знаковая арифметика, асинхронные сбросы, двунаправленные выводы и несколько доменов такта.
- [ ] Переименование порта с предложением атомарно обновить соответствующие CST, вместо оставления старого имени для ручной проверки.

[Подробный концепт и критерии расширения](schematic-authoring-plan.md). Поведение генератора проверяется независимыми моделями в Icarus: 6144 комбинационных вектора и отдельная последовательность регистра/счётчика.

## 5. Выводы платы и физический контракт — первая версия готова

В Quartus назначения портов выполняет **Pin Planner**, который сохраняет их в QSF. Chip Planner отвечает за физическое планирование ресурсов. Yosis реализует назначение выводов с сохранением в Gowin CST. [Документация Intel](https://www.intel.com/content/www/us/en/docs/programmable/683143/24-1/generating-settings-files.html).

- [x] Карта корпуса QN88 с 88 контактами, данными 66 I/O из Apycula 0.32, банками, текущими назначениями и функциями платы.
- [x] Порты из настоящего нетлиста Yosys, каждый бит шины отдельно; сохранение номеров/направления диапазона.
- [x] Выбор сигнала → контакт → назначение IO_LOC/IO_PORT; текстовый CST доступен рядом.
- [x] Масштабирование колесом/кнопками, перемещение фона, возврат к полному виду.
- [x] Запрет питания, земли, JTAG и служебных контактов; проверка направления штатных кнопок/LED/UART и конфликтов между файлами CST.
- [x] LVCMOS33 и подтяжки; сохранение других электрических свойств и комментариев.
- [x] Изменение CST сохраняет список HDL-портов; редактирование HDL требует повторного анализа.
- [ ] Дополнительные платы/корпуса, отдельная карта разъёмов платы, разрешения для разных напряжений банков.
- [ ] Дифференциальные пары и полный набор электрических стандартов в графическом режиме. Сейчас доступны в тексте CST.

- [x] Независимая модель ROM/NOR; native harness настоящего C-обработчика, 14 групп/20 000 пакетов с UBSan; пересобран MCU-бинарник.

- [ ] Матрица штатных ревизий Tang Nano 20K и Windows/Linux/Chromium.

Ранее пользователь подтвердил чередование двух групп по три LED после загрузки Yosis через установленные Gowin-инструменты. Это отдельный аппаратный результат и не закрывает приёмку нового браузерного установщика. Публикация, наличие дескрипторов и тесты протокола не заменяют эту проверку.

## Порядок продолжения

1. Конструктор и Pin Planner прошли браузерную приёмку; результаты проверок и первая Git-версия сохранены.
2. Развить симуляционную лабораторию: произвольное время воздействий, ожидаемые значения, обратная связь RTL → диаграммы. Переход сигнал → RTL уже работает.
3. Добавить учебные миссии для конструктора и физических выводов; затем главы про частоту/дребезг/память/интерфейсы.
4. Закрыть аппаратный цикл DirtyJTAG и Linux deployment smoke на соответствующем оборудовании.
5. Маршруты кристалла и пользовательские подмодули конструктора.
6. Конкретная RISC-V SoC, C/BRAM, затем SDRAM и аппаратная проверка.

Каждый шаг должен иметь программный критерий приёмки. Для функций платы отдельно фиксируется подтверждённое наблюдение на оборудовании. Текущие проверки: [verification.md](verification.md); краткий отчёт: [status-report.md](status-report.md).
